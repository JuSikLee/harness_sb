# 글쓰기 첨삭 에이전트 — Spec (v2)

> v2 표기: `(v2:A~F)`는 v1 실행 분석에서 드러난 스펙 빈칸, `(v2:#n)`은 v1 코드 상단 `# ASSUMED` n번째 결정을 스펙으로 옮긴 줄이다.

## 1. outcomes — 원하는 결과
(이 작업이 끝났을 때 무엇이 만들어져야 하는가)

결과물: outputs/review_{date}_v2_{NN}.docx 한 파일.
이 .docx는 다음 4개 섹션 구조를 가진다.
1. 헤더 + 면책: "# 글쓰기 첨삭 --- {원본 파일명} --- {날짜}" + "이 첨삭은 최종 결정이 아니며, 작성자의 의도가 우선합니다."
2. "전반 진단" 섹션: 4항목(문법 · 논리 · 톤 · 근거) 각각에 ★/△/√ 표시 + 한 줄 코멘트(원문 인용 포함).
3. "구간별 수정안" 섹션: 수정이 필요한 구간 3~5개. 각 항목은 "원문 인용 → 대안 1~2개 → 한 줄 이유" 형식.
4. "종합" 섹션: 한 단락(150자 이내). 감정 1줄 + 핵심 개선 포인트 1줄.

함께 생성되는 파일: runs/run_{date}_v2_{NN}.json --- Spec verification criteria로 채점한 결과 (pass/fail + 코멘트)

- (v2:A) 모든 원문 인용은 진단 코멘트·수정안 구분 없이 반드시 `「…」`로 감싼다. 코멘트 안에 인용이 있어도 `「」` 표기를 생략하지 않는다.
- (v2:C, v2:#6) 등급 정의: ★ = 먼저 손봐야 할 문제(독자가 오해하거나 문장이 성립하지 않는 수준), △ = 다듬으면 좋은 부분, √ = 특별한 문제 없음. ★/△는 문제 신호이며 수정 대상이 된다.
- (v2:D, v2:#29) 파일명은 `outputs/review_{date}_v2_{NN}.docx`, `runs/run_{date}_v2_{NN}.json`이다. NN은 두 자리 0 패딩으로 01부터 시작하며, 두 디렉토리에서 같은 날짜의 `_v{NN}` 파일 중 가장 큰 번호 + 1을 쓴다. docx와 json은 항상 같은 번호를 공유하고, 번호 없는 옛 형식 파일은 번호 계산에 포함하지 않고 건드리지도 않는다.
- (v2:#8) 진단 인용문은 근거가 되는 한 문장 안의 부분 문자열이며 최대 80자다. 모델이 준 인용이 원문에 없으면 해당 문장 앞 80자로 대체하고, 말줄임표는 쓰지 않는다. √ 등급 항목도 대표 문장 1개를 인용한다.
- (v2:#12) 수정안 인용문은 대상 문장 전체이며, 80자를 넘으면 앞 80자만 쓴다.
- (v2:#14) 코멘트는 줄바꿈 없는 한 문장 120자 이내, 수정안의 이유는 80자 이내로 쓴다.
- (v2:#15) 종합 단락은 감정 1줄과 핵심 개선 포인트 1줄을 이어 붙여 150자 이내로 쓴다.
- (v2:#16) docx 서식은 제목 Heading1, 섹션 제목 Heading2, 본문 일반 단락이며 글꼴은 맑은 고딕 10.5pt다. "한 페이지"는 분량 억제로만 노력한다.
- (v2:#17) 진단 줄 형식은 "문법 — △ — 코멘트", 수정안 줄 형식은 "1. 「원문」 → 대안: A / B → 이유: ..."로 고정한다.
- (v2:#18) 헤더 제목의 {원본 파일명}은 draft.md 파일명만 쓴다.
- (v2:#27) run JSON 스키마는 {date, input, output, result, deterministic[], inference[], step_log[]}이다.
- (v2:#28) {date}의 기본값은 오늘(로컬 날짜)이며 `--date YYYY-MM-DD`로 덮어쓸 수 있다.

## 2. scope boundaries — 범위 · 제외 사항
(포함하지 않을 것들)

**포함:**
- inputs/draft.md(첨삭 대상 글), inputs/author_intent.md(작성 의도) 두 파일을 입력으로 사용한다.
- 4항목(문법 · 논리 · 톤 · 근거) 진단을 수행한다.
- 수정이 필요한 구간 3~5개에 대해 "원문 인용 → 대안 1~2개 → 한 줄 이유" 형식의 대안을 제시한다.

**미포함:**
- 점수 매기기 · 정량 점수 출력 (예: "이 글은 70점")
- 절대 평가 형태의 정량 점수 출력
- 사실 검증
- 창의성 평가 · 작가 스타일 비판

진단은 ★/△/√ 세 단계 신호로만 표시하고, 정량 점수는 의도적으로 제외한다. 숫자는 절대 평가의 인상을 주기 쉽지만, 첨삭의 목적은 작성자가 의견을 선택적으로 받아들여 글을 개선하도록 돕는 데 있으므로 신호 기반 3단계 표현이 더 적절하다.

- (v2:F) 이 섹션에서 말하는 "등급"은 점수·숫자 평가만 가리킨다. §1·§6의 ★/△/√ 등급 기호는 허용되는 신호 표시이며 미포함 대상이 아니다.

## 3. constraints — 제약
(지켜야 할 것)

- 출력 언어: 한국어
- 모델: 클로드 코드 Sonnet 사용. sub-agent · multi-step 흐름 사용 안 함 (이 작업은 단일 에이전트로 충분)
- 외부 API 호출 금지
  - 입력은 inputs/ 폴더의 로컬 파일만 사용.
- 입력 본문(draft.md)은 3,000자 이내를 가정한다.

- (v2:E) "sub-agent · multi-step 흐름 사용 안 함"은 별도 sub-agent 정의와 에이전트 간 위임을 쓰지 않는다는 뜻이다. §5의 단계를 한 스크립트가 순차로 진행하며 단계마다 모델을 호출하는 것은 허용한다.
- (v2:#1) LLM 호출은 API SDK 대신 로컬 `claude -p --model sonnet` CLI를 subprocess로 실행해서 한다.
- (v2:#2) 같은 단계 안의 항목별 호출은 스레드 4개까지 병렬로 실행해도 된다.
- (v2:#16) python-docx는 설치돼 있지 않다고 가정하고, zipfile로 최소 OOXML을 직접 작성한다.
- (v2:#19) LLM 호출당 타임아웃은 240초이고, 실패하면 1회 재시도한다(총 2회). 토큰 한도는 CLI 기본값에 맡긴다.
- (v2:#20) 입력 본문이 3,000자를 넘으면 경고만 로그에 남기고 그대로 진행한다.
- (v2:#30) 실행은 동시에 하나만 돈다고 가정하며 파일 락은 두지 않는다.

## 4. prior decisions — 이미 정한 것
(논의 끝난 결정)

- 첨삭 톤: "같이 일하는 동료"
  - 평가 · 판정이 아니라 함께 다듬는 시각. ("못했다" · "잘했다" · "더 노력해야" 같은 평가성 표현, 지시 · 명령형 어조 금지. §6 추론 규칙이 이를 자동 검사합니다)

- (v2:B) 금지 대상은 코멘트·수정안에 쓰인 "~하세요", "~해야 합니다" 같은 지시·명령형 어미 자체와 평가어다. 작성 의도에 적힌 문체 기준을 설명하는 표현은 학생 지도 어조가 아니므로 예외로 본다.
- (v2:#13) 코멘트 어조는 "함께 다듬는 동료" 시각의 합니다체와 제안형("~해 보면 어떨까요", "~로 읽힙니다")으로 쓴다. 평가어와 명령형은 프롬프트로 금지한다.

## 5. task breakdown — 구체 작업 단위
(어떤 단계로 진행하는가)

1. **입력 읽기** --- inputs/draft.md와 inputs/author_intent.md를 읽고, 본문은 문장 단위로 인덱스를 단 리스트로, 작성 의도는 dict로 정리한다.
   - 입력: 폴더 경로 / 출력: { sentences: [...], intent: {...} }
2. **4항목 진단** --- 본문 전체를 문법 · 논리 · 톤 · 근거 4가지 시각에서 점검하고, 각 항목의 ★/△/√ 등급과 한 줄 코멘트(원문 인용 포함)를 만든다.
   - 입력: 1단계의 sentences · intent / 출력: { 문법, 논리, 톤, 근거 } 각각 등급+코멘트
3. **수정 구간 추출** --- 2단계 진단에서 ★ 또는 △가 나온 부분의 구체 문장 인덱스 3~5개를 골라낸다.
   - 입력: 1단계 · 2단계의 결과 / 출력: 수정 대상 문장 인덱스 리스트
4. **수정안 생성** --- 3단계에서 고른 구간 각각에 대해 대안 1~2개와 한 줄 이유를 만든다. 형식은 "원문 인용 → 대안 → 이유"로 고정.
   - 입력: 수정 대상 인덱스 + 원문 / 출력: revision 배열
5. **한 페이지 출력** --- outputs/review_{date}_v{NN}.docx를 스펙 §1(outcomes)의 4섹션 구조로 작성한다. 모든 진단 · 수정안에 원문 인용을 함께 표시.
   - 입력: 위 모든 산출물 / 출력: .docx 파일

각 단계는 구현 · 실행 단위에서 독립적이어야 하고, 한 단계의 부분 실패가 다음 단계를 멈추지 않게 한다. 예를 들어 2단계 진단이 4항목 중 일부만 등급화에 성공해도 4단계 수정안 생성은 그 항목들에 대해서만이라도 진행되어, 사용자가 부분 첨삭이라도 받게 하기 위함이다. 최종 합격 여부는 §6 verification criteria가 출력 .docx 전체에 대해 결정론 · 추론 규칙을 모두 적용해 판정한다.

- (v2:#3) 문장 분할은 줄(문단) 단위로 먼저 나눈 뒤 마침표·물음표·느낌표(. ? !) 뒤 공백에서 자른다. '#'로 시작하는 제목 줄은 문장 목록에서 제외하고 모델에 맥락으로도 전달하지 않는다.
- (v2:#4) 문장 인덱스는 0부터 시작하고, 문장 텍스트는 draft.md 원문의 부분 문자열 그대로 유지한다(정규화 없음).
- (v2:#5) author_intent.md는 줄바꿈 또는 " / "로 구분된 "키: 값" 조각을 dict로 만들고, 그 형태가 아닌 조각은 "기타_N" 키에 담는다.
- (v2:#7) 진단은 4항목을 각각 별도 LLM 호출로 처리해 항목별로 독립 실패할 수 있게 한다.
- (v2:#9) 수정 구간은 ★ 항목의 문제 문장을 먼저, △ 항목을 다음으로 모아 중복을 제거하고 앞에서 최대 5개를 고른다. 3개 미만이면 LLM에 추가 후보 문장을 1회 요청하고, 그래도 3개 미만이면 있는 만큼만 진행한다.
- (v2:#10) 항목당 문제 문장 후보는 최대 2개다.
- (v2:#11) 대안은 문장 하나를 대상으로 앞뒤 1문장 맥락과 작성 의도를 주고, (a) 의미는 유지하며 문제만 고친 안, (b) 필요할 때만 구조를 바꾼 안 순으로 1~2개를 낸다.
- (v2:#15) 종합 단락 생성이 실패하거나 150자를 넘으면 고정 문구(하드코딩)로 대체한다.
- (v2:#21) 실패한 항목·구간은 건너뛰고 step_log에 남긴다. 진단에 실패한 항목은 docx에 "(진단 실패)" 줄로 표시하되 등급 기호를 넣지 않는다.

## 6. verification criteria — 합격 기준
(결과가 통과인지 어떻게 판정하는가)

규칙은 결정론 4개 + 추론 3개, 총 7개이며 합격선도 이 7개 기준으로 정한다.

**결정론적 규칙 (4개, 코드로 검사 가능 --- 먼저 실행)**

1. 출력 파일에 4개 섹션(헤더+면책 · 전반 진단 · 구간별 수정안 · 종합)이 모두 있다.
2. 전반 진단에 정확히 4개 항목(문법 · 논리 · 톤 · 근거)이 있고, 각 항목에 ★/△/√ 중 하나의 등급 기호가 붙어 있다.
3. 구간별 수정안은 3~5개이며, 각 항목이 "원문 인용 → 대안 → 한 줄 이유" 세 부분을 모두 가진다.
4. 첫 번째 섹션(헤더)에 면책 문구("이 첨삭은 최종 결정이 아니며···")가 있다.

**추론적 규칙 (3개, LLM 판단 --- 결정론 통과 후 실행)**

5. 모든 진단 · 수정안의 인용문이 inputs/draft.md 본문에 공백 · 구두점까지 정확히 일치하는 형태로 존재한다.
6. 4항목 진단의 등급(★/△/√)이 코멘트 내용과 일관된다 --- 예: 코멘트가 "문제가 많다"는 취지인데 등급이 √이면 fail.
7. 코멘트 · 수정안 톤이 평가성 표현("잘했다" · "못했다" · "더 노력해야")이나 선생-학생 어조로 흐르지 않는다.

**합격선**

규칙 1~7 모두 통과 시 pass. 결정론 규칙(1~4) 중 1개라도 어긋나면 즉시 fail로 처리하고 추론 단계(5~7)로 넘어가지 않는다. 추론 규칙(5~7)에서 어긋난 항목은 fail로 기록하되 어긋난 이유를 코멘트로 함께 첨부한다.

- (v2:A) 규칙 5의 검사 대상은 진단 코멘트와 수정안에서 `「」`로 감싼 문자열 전부이며, 진단 4개 + 수정안 개수만큼의 인용이 모두 검사에 포함돼야 한다. 검사된 인용 수와 기대 수가 다르면 fail이다.
- (v2:B) 규칙 7은 §4의 금지 대상(지시·명령형 어미 자체와 평가어)이 코멘트·수정안에 있는지를 기준으로 판정한다. 작성 의도의 문체를 설명하는 표현은 예외다.
- (v2:C) 규칙 6은 §1의 등급 정의(★/△/√)를 판정 기준으로 쓴다. 4항목의 등급이 모두 같을 때는 각 코멘트가 그 등급의 정의를 충족하는지를 항목별로 확인한다.
- (v2:#22) 규칙 1의 섹션 판별은 Heading1 제목 1개("글쓰기 첨삭"으로 시작)와 Heading2 섹션 제목 3개("전반 진단" · "구간별 수정안" · "종합")의 일치로 한다.
- (v2:#23) 규칙 5는 LLM 판단이 원칙이지만 기계적 부분 문자열 검사 결과를 증거로 함께 주고, 기계 검사에서 불일치가 있으면 LLM이 pass라 해도 fail로 기록한다.
- (v2:#24) 규칙 6·7의 입력은 진단 4줄과 수정안 전체 텍스트를 그대로 LLM에 주고 JSON 판정을 받는다.
- (v2:#25) 추론 규칙에서 LLM 호출 자체가 실패하면 pass가 아니라 fail("판정 불가")로 기록한다.
- (v2:#26) 결정론 규칙이 fail이면 추론 규칙은 실행하지 않고 "skipped"로 기록하며 전체 결과는 fail이다.
